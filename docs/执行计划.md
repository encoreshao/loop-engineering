## P0 准备与契约冻结

先把迁移期间不能变的东西写下来，后面每一步都拿它做验收。

- [x] 新建 cargo workspace：`crates/core`、`crates/server`、`crates/cli`，产出单个 `loopx` 二进制
- [x] CI：`cargo test`、`cargo clippy -D warnings`、`cargo fmt --check`，构建 arm64 + x86\_64 universal binary
- [x] 写下 JSON 契约：`projects.json`、`topics.json`、`ai_cli.json`、`status.json`、`messages.json`，以及 `~/.gitlab/config.json`、`~/.slack/config.json`
- [x] 列出 dashboard 的全部 HTTP API（路径、方法、请求和响应）
- [x] 记录每个 `bin/*.py` 和 shell 脚本的 CLI 参数与输出格式
- [x] 改造 pytest：被测命令从环境变量读取（如 `LOOPX_BIN`），同一套测试能跑 Python 版和 Rust 版

**验收**：契约文档入库；pytest 在 Python 版上全绿，并可切换被测命令。

## P1 CLI 与脚本迁移

每替换一个脚本，就把对应测试切到 `loopx`，全绿后删掉旧文件。

| 现有脚本 | 新子命令 |
| --- | --- |
| `bin/loop_config.py` | `loopx config` |
| `bin/list_assigned_issues.py` | `loopx issues list` |
| `bin/track_new_comments.py` | `loopx issues comments` |
| `bin/project_memory.py` | `loopx memory` |
| `bin/topic_config.py`、`bin/topic_seen.py` | `loopx topic` |
| `bin/slack_notify.py` | `loopx notify` |
| `bin/scripts/new_worktree.sh` | `loopx worktree new` |
| `bin/scripts/open_merge_request.sh` | `loopx mr open` |
| `run-loop.sh` | `loopx run` |
| `run-topic-monitor-loop.sh` | `loopx topic run` |

**进度（rust-migration 分支）**：P1 的全部命令已在 `loopx` 中实现并有测试：`config`、`issues list|comments`、`memory`、`topic config|seen|run`、`notify`、`worktree new`、`mr open`、`gitlab`（取代 gitlab-config skill 的 `gitlab_api.py`/`gitlab_cache.py`）、`events`、`ledger`、`status`、`risk`、`cost`、`learning`、`memory-store`、`loops`、`ai-cli`，以及 `run`（取代 `run-loop-now.sh`，含 GitLab loop 与 topic loop 的完整 Rust runner、gate 模式开 MR）和 `scheduler`（取代 `loop_scheduler.py`）。契约测试同时跑 Python 与 Rust：`LOOPX_BIN=target/debug/loopx python3 -m pytest tests/test_cli_contract_*.py tests/test_e2e_loopx_*.py`。Agent 用的指令在 `instructions/loopx/`（命令已换成 `loopx ...`），Python 版指令保持不动，P2 删除 Python 时再替换 `instructions/`。旧的 Python/shell 文件暂不删除：dashboard 等仍在 import 它们。待办：launchd plist 入口切换放到 P5 的安装脚本里一起做；`loopx run` 对未移植的 loop（inbox triage、LinkedIn、LoopKit 插件）会回退到 `python3` 入口。

- [x] 按上表顺序逐个迁移，`config` 最先，`run` 最后
- [x] `loopx mr open` 保留只接受 `loop/issue-*` 分支的检查
- [x] `loopx run` 保留逐个处理 issue、不并行、失败通知 Slack 的行为
- [x] 更新 `LOOP_INSTRUCTIONS.md` 和 `TOPIC_MONITOR_INSTRUCTIONS.md` 的命令白名单
- [x] launchd plist 的入口改为 `loopx run` 和 `loopx topic run`

**验收**：pytest 对 Rust 版全绿；手动跑一次真实 GitLab loop 和 topic monitor，结果和 Python 版一致。

## P2 服务端与 Web 模式

这一阶段结束后，Web 模式就是完整产品，Python 全部移除。

- [x] `loopx serve`：用 axum 复刻现有 dashboard API，`rust-embed` 内嵌现有前端
- [x] `/api/events`（SSE）：用 `notify` 监听 `status.json` 和 `messages.json`，推送状态变化
- [x] 启动时写 `~/.loop-engineering/loopx.lock`（PID、端口、版本），并提供 `/api/version`
- [x] `/api/approvals`：开 MR 前的审批与 escalation 状态，带超时
- [x] Daemons 页面的 launchd 管理（加载、卸载、改计划）迁到 Rust
- [x] Activity 页内嵌的 chat assistant（`chat-tool`）迁到 Rust
- [ ] Web 模式提醒：浏览器通知，加上已有的 Slack 推送（待办：浏览器通知需要往页面注入脚本，而 golden UI 要求与 Python 逐字节一致，需先定方案）
- [ ] 删除所有 Python 代码，README 改为 `loopx` 用法（待办：最后一步；pytest 契约测试仍以 Python 脚本为对照，真机验收通过后再删）

**验收**：Web 模式下全部页面与现状一致；SSE 断线能自动重连；仓库里不再有 Python 运行时依赖。

## P3 LoopX.app（Swift）

P0 冻结契约后就可以开始，先对接 mock SSE，等 P2 完成再和真实后端联调。

- [x] `NotchPanel`：无边框 `NSPanel`，按 `safeAreaInsets` 和 `auxiliaryTopLeftArea` 定位，跨 Space 和全屏可见
- [x] 无刘海屏：可拖到屏幕边缘的 HUD；多屏时提醒只出现在指针所在的屏幕
- [x] 收起与展开动画：悬停展开，SwiftUI spring 动画
- [x] 状态映射：空闲、运行中、escalate、MR 已开、失败，各自的样式与动作
- [x] 审批 UI：Allow / Deny，对接 `/api/approvals`
- [x] SSE 客户端：断线重连，app 休眠唤醒后恢复
- [x] Dashboard 窗口：WKWebView 加载 `loopx` 的页面
- [x] 后端发现：读 `loopx.lock`，已有后端就连接；没有就用 `SMAppService` 注册内置 `loopx`；版本旧时提示接管
- [x] 菜单栏图标与设置：开机启动、显示模式、隐藏快捷键

**验收**：有刘海和无刘海屏都表现正常；后端重启、断网、睡眠唤醒后状态能恢复；和浏览器同时打开 dashboard 不冲突。

## P4 OAuth 与 Keychain

依赖 P2 的服务端；token 交换全部在本地的 `loopx` 里完成。

- [x] 决定回调端口：固定 dashboard 端口，或单独开一个固定的回调端口
- [x] 确认 LinkedIn 是否接受 `http://127.0.0.1` 回调，并在开发者后台注册
- [x] Google：桌面客户端，loopback 回调 + PKCE
- [x] LinkedIn：授权码流程，回调到 `/oauth/callback`
- [x] token 存 Keychain，过期自动刷新
- [x] 把 `~/.gitlab/config.json`、`~/.slack/config.json` 里的明文 token 迁入 Keychain，JSON 只保留引用
- [ ] Web 模式在浏览器里跳转授权；app 模式用 `ASWebAuthenticationSession`（待办：Web 模式已通；app 内授权尚未接入）

**验收**：两种模式都能完成 Google 和 LinkedIn 登录；重启后无需重新授权；配置文件里不再有明文 token。
